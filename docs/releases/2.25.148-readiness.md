## Release stop and later merge sequence

`auto-tag.yml` now requires the repository variable `DESKTOP_RELEASE_ENABLED` to compare equal to `true` before its entire job can run. Unset or false blocks checkout, tag creation and dispatch. `build-desktop.yml` independently gates tag/publish events and its release upload job. Explicit build-only dispatch remains possible, but is not authorized by this task. No repository variable or environment protection was changed or verified here.

When the release opt-in is enabled, a matching main push can still create `v2.25.148` and dispatch `build-desktop.yml` at main with `publish_mode=publish`. Existing tags without a release can also dispatch. **Do not enable the opt-in merely to merge source.** Verify it is unset/false, or pause the old auto-tag workflow before any version-bearing merge. Re-enabling a workflow does not replay old pushes; a later matching push can release.

Publish mode requires Apple signing and notarization prerequisites; missing values fail before building instead of choosing ad-hoc/unsigned publication. Build-only fallback artifacts are not public-release acceptance. The upload job creates or resumes a **draft** release, rejects existing public releases, uploads and verifies payloads, and leaves final publication to the maintainer after artifact acceptance. Draft-state reads and later edits/uploads are separate GitHub API calls. Wait for the entire upload/verification run to finish before manually publishing; do not publish a draft concurrently with that run. Declaring `environment: release` in YAML does not prove required reviewers are configured; verify protections separately.

Do not run `npm run release:prepare`: it creates tags on main even without `--push`. Do not run `pr-closeout.sh`: it arms auto-merge.

## Release blockers beyond this source repair

Independent review identified two existing ref-binding limitations that must be repaired and tested before enabling or dispatching release automation:

- Build-only context still supplies a version tag and the build checkout prefers it. An absent 148 tag can stop candidate builds; an existing tag can select old source instead of the intended candidate commit. Do not use the current build-only path as proof of final-head artifacts until checkout is bound to the explicit candidate SHA.
- Recovery dispatch runs at main and currently supplies `github.sha` to release metadata while the build checks out `release_tag`. If those refs differ, the manifest/provenance can name main instead of the built tag. Resolve the tag commit and bind context, artifact source and manifest to that same commit; add differing-main/tag tests before publication.
